This is the week where everything pays off. In Chapter 2 we met gradient descent in one dimension, in Chapter 3 we wrapped it into a reusable function, and in Chapter 4 we learnt to draw pictures of what our code is doing. This week we put those tools to work on the problem that underlies an enormous amount of modern statistics: Fitting a model is minimising a function.

Maximum likelihood, least squares, penalised regression, neural networks: behind each of them sits an optimisation problem, and behind most of the algorithms that solve those problems sits some descendant of gradient descent. By the end of this chapter you will have met the whole family: plain gradient descent, its stochastic cousin, preconditioning, and the quasi-Newton method BFGS that the built-in optimisers of both languages (R’s optim() and Python’s scipy.optimize.minimize()) use in practice.

5.1 Gradient descent, again

Quick recap. We want to minimise a differentiable function f : \mathbb{R}^d \to \mathbb{R}. The gradient \nabla f(\mathbf{x}) points in the direction of steepest increase, so we repeatedly take a small step the other way:

\mathbf{x}_{n+1} = \mathbf{x}_n - \gamma \, \nabla f(\mathbf{x}_n),

where \gamma > 0 is the step size (machine learning people say learning rate). In Chapter 3 we packaged this into grad_descent(f, grad, x0, gamma, n). Here it is again with two upgrades. First, instead of returning only the final point, it records the whole trajectory, because this week we want to watch the algorithm work. Second, it drops f from the arguments: look at the update rule, and notice that the objective itself is never evaluated. The gradient is all the algorithm needs; the function is for us (plots, diagnostics), and we will call it ourselves when we want it.

Algorithm 5.1 states the method formally; the code adds only the bookkeeping that records the trajectory.

Algorithm 5.1: Gradient descent

Input: the gradient \nabla f of an objective f : \mathbb{R}^d \to \mathbb{R}, start point \mathbf{x}_0, step size \gamma > 0, number of steps n_{\text{steps}} (the code’s n).

Output: the trajectory \mathbf{x}_0, \mathbf{x}_1, \dots, \mathbf{x}_{n_{\text{steps}}}; the final iterate approximates the minimiser.

  1. for t = 1, 2, \dots, n_{\text{steps}}:
    1. \mathbf{x}_t \leftarrow \mathbf{x}_{t-1} - \gamma \, \nabla f(\mathbf{x}_{t-1})
  2. return \mathbf{x}_0, \mathbf{x}_1, \dots, \mathbf{x}_{n_{\text{steps}}}

R

grad_descent <- function(grad, x0, gamma, n) {
  # one row per iterate, one column per coordinate
  path <- matrix(NA_real_, nrow = n + 1, ncol = length(x0))
  path[1, ] <- x0
  for (i in 1:n) {
    path[i + 1, ] <- path[i, ] - gamma * grad(path[i, ])
  }
  # return a data frame ready for ggplot: one row per iterate
  out <- as.data.frame(path)
  names(out) <- paste0("x", seq_along(x0))
  out$iter <- 0:n
  out
}

Python

import numpy as np
import pandas as pd

def grad_descent(grad, x0, gamma, n):
    # one row per iterate, one column per coordinate
    path = np.full((n + 1, len(x0)), np.nan)
    path[0] = x0
    for i in range(n):
        path[i + 1] = path[i] - gamma * grad(path[i])
    # return a data frame ready for plotting: one row per iterate
    out = pd.DataFrame(path, columns=[f"x{j + 1}" for j in range(len(x0))])
    out["iter"] = range(n + 1)
    return out

Note for Python: the R loop runs i = 1, ..., n and fills rows 2, ..., n + 1; the Python loop runs i = 0, ..., n - 1 and fills rows 1, ..., n: the same trajectory, one index base apart (Chapter 1’s indexing note at work).

Note the functional style from Chapter 3: grad is an argument. The same dozen lines will minimise a toy parabola now and a logistic regression likelihood later, without changing a character.

Let us try it on a friendly two-dimensional bowl,

f(x_1, x_2) = (x_1 - 1)^2 + 2\,(x_2 + 1)^2, \qquad \nabla f(x_1, x_2) = \begin{pmatrix} 2(x_1 - 1) \\ 4(x_2 + 1) \end{pmatrix},

5.1.1 Why the step size is hard

The step size \gamma is doing a lot of quiet work. To expose it, we use a function that is deliberately ill-conditioned (much steeper in one direction than the other):

f(x_1, x_2) = \frac{x_1^2}{2} + \frac{10\, x_2^2}{2}, \qquad \nabla f(x_1, x_2) = \begin{pmatrix} x_1 \\ 10\,x_2 \end{pmatrix}.

Think of a long narrow valley: gentle along x_1 (curvature 1), steep across it in x_2 (curvature 10). Watch what three different step sizes do, starting from (-9, 1.5).

5.1.1.1 The condition number

There is a clean piece of intuition behind this. For a quadratic, gradient descent in each coordinate multiplies the error by (1 - \gamma \lambda) per step, where \lambda is the curvature in that direction. These directional curvatures are exactly the eigenvalues of the Hessian of f, its symmetric matrix of second derivatives \nabla^2 f: the eigen() from Chapter 1 (Python: np.linalg.eig()), quietly reappearing as promised. Formally, collect the eigenvalues of the Hessian into the set \{\lambda_1, \lambda_2, \dots, \lambda_d\} and pick out its two extremes:

\lambda_{\max} = \max_{j} \lambda_j \quad \text{(the steepest curvature)}, \qquad \lambda_{\min} = \min_{j} \lambda_j \quad \text{(the flattest)}.

Stability requires |1 - \gamma \lambda_j| < 1 for every direction j, and the steepest one is the binding constraint:

\gamma < \frac{2}{\lambda_{\max}}.

Progress in the flattest direction, meanwhile, is governed by \lambda_{\min}: per step its error shrinks by (1 - \gamma\lambda_{\min}), at best about (1 - \lambda_{\min}/\lambda_{\max}). The tension between the two extremes is measured by their ratio,

\kappa = \frac{\lambda_{\max}}{\lambda_{\min}} \qquad \text{(the condition number)},

which controls how many iterations you need: as \kappa grows, the iteration count grows in proportion.

In our example, the valley has curvatures 1 (along x_1) and 10 (across it, along x_2), so \lambda_{\max} = 10 and the stability bound is \gamma < 2/10 = 0.2: exactly why 0.18 scraped through and 0.25 exploded. Its condition number is \kappa = 10/1 = 10, and that is already annoying: the zig-zag panel is what \kappa = 10 looks like.

If you have met condition numbers in a linear algebra course, you may know a different-looking definition: \kappa(A) = \sigma_{\max}(A) / \sigma_{\min}(A), a ratio of singular values, measuring how much solving A\mathbf{x} = \mathbf{b} amplifies small errors in the inputs. There is no conflict. Our \kappa is the condition number of the Hessian, and a Hessian is always symmetric (mixed partial derivatives commute) and, at a minimum, positive (semi-)definite; for such matrices the singular values are the eigenvalues, so \lambda_{\max}/\lambda_{\min} and \sigma_{\max}/\sigma_{\min} are the same number. (For a general symmetric matrix, \sigma_i = |\lambda_i|; eigenvalues and singular values genuinely part ways only for non-symmetric matrices, which a Hessian never is.) One notation warning for further reading: optimisation texts typically write L = \lambda_{\max} and \mu = \lambda_{\min}, calling them the smoothness and strong-convexity constants, and state the condition number as L/\mu; same objects, different costume.

The singular-value view also explains why statistical problems are so often ill-conditioned. A model fit through a design matrix X (Challenge 1.1’s least squares; the logistic regression of Section 5.1.2, where a diagonal matrix of observation weights gets pinched between X^\top and X) has a Hessian of the form X^\top X / n, and the eigenvalues of X^\top X are the squared singular values of X. Whatever imbalance the columns of X carry, the optimisation problem therefore suffers it twice over: one covariate in grams and another in kilograms (a scale ratio of just 10^3) can already push \kappa past 10^6, and plain gradient descent simply stops being a usable tool. At the extreme \sigma_{\min} = 0, \kappa is infinite and X^\top X is exactly the singular matrix that Chapter 1 warned cannot be inverted; a huge \kappa means nearly so. This is why Exercise 5.3 will ask you to stare at the column scales of its design matrix. Hold that thought; ill-conditioning is the villain for the rest of the chapter.

  X <- as.matrix(path[, grep("^x", names(path))])

def steps_to_tol(path, target, tol=1e-3):
    X = path.filter(regex="^x").to_numpy()
    dist = np.sqrt(((X - target)**2).sum(axis=1))
    hit = np.nonzero(dist < tol)[0]
    return np.nan if len(hit) == 0 else int(path["iter"].iloc[hit[0]])

5.1.2 Estimation is optimisation

So far f has been a toy. Here is why statisticians care. A huge share of estimators are defined as the minimiser of an average loss over the data:

\hat{\theta} = \arg\min_{\theta} L(\theta), \qquad L(\theta) = \frac{1}{n} \sum_{i=1}^{n} \ell_i(\theta),

where \ell_i(\theta) measures how badly the parameter \theta explains observation i. You have met one member of this family already: least squares, with \ell_i(\boldsymbol\beta) = \tfrac{1}{2}(y_i - \mathbf{x}_i^\top \boldsymbol\beta)^2 and gradient \nabla L(\boldsymbol\beta) = \tfrac{1}{n} X^\top (X\boldsymbol\beta - \mathbf{y}). Least squares is also the family’s great exception: setting its gradient to zero gives the normal equations X^\top X \boldsymbol\beta = X^\top \mathbf{y}, a linear system that solve() (np.linalg.solve() in Python) dispatches in one line, with no iteration in sight. That is exactly the magic formula \hat{\boldsymbol\beta} = (X^\top X)^{-1} X^\top \mathbf{y} you used in Challenge 1.1 of Chapter 1, and the reason this chapter spends no more time on it. Almost no other model is so lucky. Our running example is the everyday kind, where no closed form exists and iterating is the only way down.

Logistic regression (negative log-likelihood). For binary y_i \in \{0, 1\} the model is \Pr(y_i = 1 \mid \mathbf{x}_i) = \sigma(\eta_i), where \eta_i = \mathbf{x}_i^\top\boldsymbol\beta is the linear predictor (the code below calls it eta) and \sigma(z) = 1/(1 + e^{-z}) is the sigmoid function, which squashes the real line into (0, 1) so that \eta_i, which can be any real number, becomes a probability. Taking -\log of the likelihood and averaging over the observations gives the loss; differentiating the loss gives the gradient:

L(\boldsymbol\beta) = \frac{1}{n}\sum_{i=1}^n \Big[ \log\!\big(1 + e^{\mathbf{x}_i^\top\boldsymbol\beta}\big) - y_i \, \mathbf{x}_i^\top\boldsymbol\beta \Big], \qquad \nabla L(\boldsymbol\beta) = \frac{1}{n} X^\top\big(\sigma(X\boldsymbol\beta) - \mathbf{y}\big),

with the rows \mathbf{x}_i^\top stacked into the design matrix X and \sigma applied elementwise. These two formulas are all the code will need. The gradient is worth reading aloud once: observation i contributes \nabla \ell_i(\boldsymbol\beta) = \big(\sigma(\eta_i) - y_i\big)\,\mathbf{x}_i, predicted probability minus observed outcome (a residual on the probability scale) times its own covariates, so observations the model already gets right contribute almost nothing while confidently wrong ones push hard; this per-observation piece is also exactly the single-sample gradient that SGD will draw at random in Section 5.1.3. Note how the least-squares gradient at the top of this section, \tfrac{1}{n} X^\top(X\boldsymbol\beta - \mathbf{y}), has the same shape: both say “X^\top times (prediction minus data)”, the fingerprint of the generalised linear model family that R’s glm() is named after. Tidy as the gradient is, setting it to zero gives equations with no closed-form solution: you must optimise numerically. This is the everyday reality of maximum likelihood.

If you’re wondering where the two formulas come from, the proof below is optional. It is worth reading once in your life, though, in particular if you are planning to continue with your studies. This derivation you will redo, with a different likelihood each time, for every model you ever fit by maximum likelihood.

[OPTIONAL] Proof: from likelihood to loss to gradient

Step 1 We write down the negative log-likelihood. Observation i is a Bernoulli trial with success probability p_i = \sigma(\eta_i), so its probability mass is p_i^{y_i} (1 - p_i)^{1 - y_i} (check it: this equals p_i when y_i = 1 and 1 - p_i when y_i = 0). Independence multiplies the contributions, -\log turns the product into a sum, and dividing by n gives the average-loss form:

L(\boldsymbol\beta) = -\frac{1}{n} \log \prod_{i=1}^n p_i^{y_i} (1 - p_i)^{1 - y_i} = -\frac{1}{n} \sum_{i=1}^n \Big[ y_i \log p_i + (1 - y_i) \log(1 - p_i) \Big].

The parameters hide inside p_i = \sigma(\eta_i), so before differentiating we rewrite everything in terms of \eta_i. Multiplying the top and bottom of \sigma(\eta) = 1/(1 + e^{-\eta}) by e^{\eta} gives \sigma(\eta) = e^{\eta}/(1 + e^{\eta}), hence 1 - \sigma(\eta) = 1/(1 + e^{\eta}), and taking logs:

\log \sigma(\eta) = \eta - \log\big(1 + e^{\eta}\big), \qquad \log\big(1 - \sigma(\eta)\big) = -\log\big(1 + e^{\eta}\big).

Substituting both into the i-th summand \ell_i of L:

\ell_i(\boldsymbol\beta) = -y_i \big[ \eta_i - \log\big(1 + e^{\eta_i}\big) \big] + (1 - y_i) \log\big(1 + e^{\eta_i}\big) = \log\big(1 + e^{\eta_i}\big) - y_i \, \eta_i,

the two logarithm terms merging because their coefficients y_i and 1 - y_i sum to one. Averaging the \ell_i:

L(\boldsymbol\beta) = \frac{1}{n}\sum_{i=1}^n \Big[ \log\!\big(1 + e^{\mathbf{x}_i^\top\boldsymbol\beta}\big) - y_i \, \mathbf{x}_i^\top\boldsymbol\beta \Big].

Step 2. We differentiate, by first noting that the derivative of \log(1 + e^{\eta}) (machine learning people call this function the softplus), is the sigmoid again:

\frac{d}{d\eta} \log\big(1 + e^{\eta}\big) = \frac{e^{\eta}}{1 + e^{\eta}} = \sigma(\eta).

Second, we note that \eta_i = \mathbf{x}_i^\top\boldsymbol\beta is linear in \boldsymbol\beta with \nabla_{\boldsymbol\beta}\, \eta_i = \mathbf{x}_i, so a term g(\eta_i) contributes g'(\eta_i)\, \mathbf{x}_i to the gradient. Applying both to \ell_i = \log(1 + e^{\eta_i}) - y_i \eta_i:

\nabla \ell_i(\boldsymbol\beta) = \sigma(\eta_i)\, \mathbf{x}_i - y_i\, \mathbf{x}_i = \big(\sigma(\eta_i) - y_i\big)\, \mathbf{x}_i .

Averaging over the sample and stacking the rows \mathbf{x}_i^\top into the design matrix X packs the sum into one matrix product:

\nabla L(\boldsymbol\beta) = \frac{1}{n} \sum_{i=1}^n \big(\sigma(\eta_i) - y_i\big)\, \mathbf{x}_i = \frac{1}{n} X^\top\big(\sigma(X\boldsymbol\beta) - \mathbf{y}\big),

with \sigma applied elementwise: exactly the two formulas claimed above. \square

Python

rng = np.random.default_rng(7432)

# --- logistic regression data: intercept + one covariate --------------------
n_log = 500
x_log = rng.normal(size=n_log)
X_log = np.column_stack([np.ones(n_log), x_log])   # design matrix: intercept + slope
beta_log_true = np.array([-0.5, 2])
p_true = 1 / (1 + np.exp(-(X_log @ beta_log_true)))
y_log = rng.binomial(1, p_true)

sigmoid = lambda z: 1 / (1 + np.exp(-z))
def nll(b):
    eta = X_log @ b
    return np.mean(np.log(1 + np.exp(eta)) - y_log * eta)

def nll_grad(b):
    p = sigmoid(X_log @ b)
    return X_log.T @ (p - y_log) / n_log

5.1.2.1 Approximate gradients

What if we cannot compute the gradient? Perhaps the loss is a black box written by someone else, or the likelihood is a page of algebra we would rather not differentiate. The descent seems stuck before it starts, but remember what a partial derivative is: the limit of a difference quotient. We can simply stop short of the limit. For a small h, each partial derivative is well approximated by its central difference:

\frac{\partial L}{\partial \beta_j}(\boldsymbol\beta) \;\approx\; \frac{L(\boldsymbol\beta + h\, \mathbf{e}_j) - L(\boldsymbol\beta - h\, \mathbf{e}_j)}{2h},

where \mathbf{e}_j has a one in position j and zeros elsewhere. A loop over the coordinates (Chapter 2) wrapped in a function that takes f as an argument (Chapter 3) turns the definition into code. How close does it get? Since here we do know the exact gradient, we can measure the approximation error directly:

R

# approximate each partial derivative of f by a central difference
num_grad <- function(f, b, h = 1e-6) {
  g <- numeric(length(b))
  for (j in seq_along(b)) {
    e <- numeric(length(b))
    e[j] <- h
    g[j] <- (f(b + e) - f(b - e)) / (2 * h)
  }
  g
}

5.1.3 Stochastic gradient descent

Look again at the gradient of the average loss:

\nabla L(\theta) = \frac{1}{n} \sum_{i=1}^{n} \nabla \ell_i(\theta).

Every single step of gradient descent touches all n observations. For our n = 500 example that is nothing; for n = 10^8 user records it means one step of GD costs a full pass over a dataset that may not even fit in memory. The sum structure suggests a cheeky fix: don’t compute the whole sum. Pick one index I uniformly at random and use \nabla \ell_I(\theta) as a stand-in for \nabla L(\theta). It is a noisy stand-in, but it is unbiased: \mathbb{E}\big[\nabla \ell_I(\theta)\big] = \nabla L(\theta). On average, it is the right direction. The update

\theta_{t+1} = \theta_t - \gamma_t \, \nabla \ell_{I_t}(\theta_t), \qquad I_t \sim \text{Uniform}\{1, \dots, n\},

is stochastic gradient descent (SGD). The step size has quietly acquired a subscript t, and it is load-bearing. With the full gradient, the steps shrink on their own as the minimum approaches, because \nabla L \to \mathbf{0} there. The noisy stand-in does us no such favour: even standing exactly at the minimiser, a randomly drawn observation pushes the iterate somewhere (only the average of the pushes is zero), so with a constant \gamma the iterates can never settle. They reach the neighbourhood of the minimiser quickly and then rattle around it forever, in a “noise ball” whose radius grows with \gamma. The cure is a decaying schedule \gamma_t: shrink the steps to strangle the noise, but not so fast that the algorithm runs out of fuel before arriving. The classical recipe (Robbins and Monro, 1951: this algorithm is older than the computer you are running it on) asks, informally, for

\sum_{t=1}^{\infty} \gamma_t = \infty \qquad \text{and} \qquad \sum_{t=1}^{\infty} \gamma_t^2 < \infty:

infinite total travel, so the iterate can reach the minimiser however far away it started, but finite total squared steps, so the noise averages out. Schedules like \gamma_t = a/(b + t) satisfy both, which is why you keep seeing that shape.

A compromise between one sample and all n is a mini-batch: average \nabla\ell_i over a random subset B of size m. Still unbiased, with variance shrinking like 1/m, at cost proportional to m. The economics are the whole point:

  • one GD step costs O(n) per-observation gradients;
  • one SGD step costs O(1) (or O(m) for a mini-batch), regardless of n.

When n is huge, SGD has taken thousands of noisy-but-useful steps before GD finishes its first.

Algorithm 5.2 states the mini-batch recipe precisely, with single-sample SGD as the special case m = 1.

Algorithm 5.2: Stochastic gradient descent (mini-batch)

Input: objective L(\theta) = \frac{1}{n} \sum_{i=1}^{n} \ell_i(\theta) with per-observation gradients \nabla \ell_i, start point \theta_0, step sizes \gamma_t > 0 (constant, or decaying like \gamma_t = a/(b + t)), batch size m, number of steps n_{\text{steps}}.

Output: the trajectory \theta_0, \theta_1, \dots, \theta_{n_{\text{steps}}}.

  1. for t = 1, 2, \dots, n_{\text{steps}}:
    1. draw a subset B_t \subseteq \{1, \dots, n\} of size m, uniformly at random, without replacement
    2. \theta_t \leftarrow \theta_{t-1} - \gamma_t \, \frac{1}{m} \sum_{i \in B_t} \nabla \ell_i(\theta_{t-1})
  2. return \theta_0, \theta_1, \dots, \theta_{n_{\text{steps}}}

Single-sample SGD is the case m = 1: step (a) draws one index I_t \sim \text{Uniform}\{1, \dots, n\} and step (b) becomes the update displayed above, \theta_t \leftarrow \theta_{t-1} - \gamma_t \, \nabla \ell_{I_t}(\theta_{t-1}). Note the index base: the step that produces \theta_t uses \gamma_t, which is exactly the code’s gamma(t), so the first update uses \gamma_1.

Here is single-sample SGD in the same functional style. The step size enters as a function of the step number t, so that constant and decaying schedules fit the same interface, and the per-observation gradient grad_i we feed it is an old friend: exactly the (\sigma(\eta_i) - y_i)\,\mathbf{x}_i derived in Section 5.1.2.

R

sgd <- function(grad_i, x0, gamma, n_steps, n_data) {
  # grad_i(theta, i): gradient of the loss at observation i only
  # gamma(t): step size at step t
  path <- matrix(NA_real_, nrow = n_steps + 1, ncol = length(x0))
  path[1, ] <- x0
  for (t in 1:n_steps) {
    i <- sample(n_data, 1)
    path[t + 1, ] <- path[t, ] - gamma(t) * grad_i(path[t, ], i)
  }
  out <- as.data.frame(path)
  names(out) <- paste0("x", seq_along(x0))
  out$iter <- 0:n_steps
  out
}

5.2 Fixing the geometry: preconditioning and BFGS

Back to the zig-zag valley of Section 5.1.1. The step size was capped by the steep direction, progress was throttled along the flat one, and the trajectory wasted its energy bouncing between walls. This section solves that geometry problem twice: first by hand, then automatically.

One classical fix earns an honourable mention on its way to the cutting-room floor: momentum, the heavy-ball trick. Give the iterate a velocity that accumulates past gradients, \mathbf{v}_{t+1} = \beta\,\mathbf{v}_t - \gamma\,\nabla f(\mathbf{x}_t), and step by \mathbf{v}_{t+1}: in the zig-zag direction successive gradients flip sign and cancel, while along the valley floor they accumulate and the iterate picks up speed. It drops straight into SGD, and mini-batch SGD with momentum is more or less the algorithm that trains deep neural networks. The two methods of this section treat the cause: the coordinates live on the wrong scales.

5.2.1 Preconditioning

If the valley is ten times steeper in x_2 than in x_1, then take steps ten times smaller in x_2. Formally, pick a symmetric positive-definite matrix P and update

\mathbf{x}_{t+1} = \mathbf{x}_t - \gamma \, P \, \nabla f(\mathbf{x}_t).

P reshapes the descent direction, stretching it in flat directions and shrinking it in steep ones. Plain gradient descent is P = I.

Algorithm 5.3 is Algorithm 5.1 with one matrix slipped in.

Algorithm 5.3: Preconditioned gradient descent

Input: objective f, gradient \nabla f, start point \mathbf{x}_0, step size \gamma > 0, a symmetric positive-definite matrix P, number of steps n_{\text{steps}} (the code’s n).

Output: the trajectory \mathbf{x}_0, \mathbf{x}_1, \dots, \mathbf{x}_{n_{\text{steps}}}.

  1. for t = 1, 2, \dots, n_{\text{steps}}:
    1. \mathbf{x}_t \leftarrow \mathbf{x}_{t-1} - \gamma \, P \, \nabla f(\mathbf{x}_{t-1})
  2. return \mathbf{x}_0, \mathbf{x}_1, \dots, \mathbf{x}_{n_{\text{steps}}}

P = I recovers Algorithm 5.1. Taking P = (\nabla^2 f)^{-1}, the inverse Hessian recomputed at every iterate, with \gamma = 1, is Newton’s method (of which more shortly).

Taking P = (\nabla^2 f)^{-1}, recomputed at every iterate, with \gamma = 1, has a name: Newton’s method. On a quadratic it finishes in one step; near the minimum of a smooth function it converges quadratically (the number of correct digits roughly doubles per iteration). So why isn’t Newton the end of the chapter?

  • Cost. In d dimensions the Hessian has d^2 entries, and applying its inverse means solving a d \times d linear system: O(d^3) per step. For a neural network with d = 10^6 parameters, the Hessian alone would need terabytes of memory.
  • Fragility. Away from the minimum the Hessian need not be positive definite, and then -H^{-1}\nabla f may not even point downhill. Making Newton robust takes real engineering.

Cheap compromises are everywhere in statistics and machine learning: use only the diagonal of the Hessian (exactly our P above: for axis-aligned problems it is the whole story, and in general it is a decent approximation); or simply standardise your covariates, which is preconditioning by a diagonal matrix before the algorithm even starts. If you remember one practical trick from this section: rescale your variables before optimising. Exercise 5.3 shows what happens if you don’t.

5.2.2 BFGS: learning the Hessian as you go

Newton’s method needs second derivatives we cannot afford. But here is the clever observation: the gradients we are already computing contain second-order information. By Taylor expansion, for nearby iterates,

\nabla f(\mathbf{x}_{k+1}) - \nabla f(\mathbf{x}_k) \;\approx\; H \, (\mathbf{x}_{k+1} - \mathbf{x}_k),

so each step tells us how the gradient changed when we moved in one particular direction: one slice of the Hessian, for free. Quasi-Newton methods maintain a running approximation B_k \approx H^{-1} and require it to explain the most recent step exactly, the secant condition:

B_{k+1} \, \underbrace{\big(\nabla f_{k+1} - \nabla f_k\big)}_{\mathbf{y}_k} = \underbrace{\mathbf{x}_{k+1} - \mathbf{x}_k}_{\mathbf{s}_k}.

BFGS (Broyden–Fletcher–Goldfarb–Shanno, 1970: four people found it independently in the same year) updates B_k by the smallest symmetric modification that satisfies the secant condition, a rank-two update: cheap matrix–vector algebra, no matrix inversion, and B_k stays positive definite so the step -B_k \nabla f_k always points downhill (provided each step actually observes positive curvature, \mathbf{y}_k^\top \mathbf{s}_k > 0: the line search inside optim() and minimize() sees to this). For the curious, the update is

B_{k+1} = \big(I - \rho_k \mathbf{s}_k \mathbf{y}_k^\top\big) B_k \big(I - \rho_k \mathbf{y}_k \mathbf{s}_k^\top\big) + \rho_k \mathbf{s}_k \mathbf{s}_k^\top, \qquad \rho_k = \frac{1}{\mathbf{y}_k^\top \mathbf{s}_k},

and we will not derive it. The point to retain is the idea: start with B_0 = I (plain gradient descent), and let each observed gradient difference teach the algorithm a bit more of the local geometry. After a handful of steps BFGS is taking nearly Newton-quality steps while having only ever evaluated f and \nabla f.

Algorithm 5.4 collects the whole loop in one place.

Algorithm 5.4: BFGS

Input: objective f, gradient \nabla f, start point \mathbf{x}_0, tolerance \varepsilon > 0 (in practice also an iteration cap, as in optim() and minimize()).

Output: the final iterate, an approximate minimiser.

  1. initialise B_0 \leftarrow I, so the first step is a plain gradient step
  2. for k = 0, 1, 2, \dots until \|\nabla f_k\| \le \varepsilon:
    1. step to \mathbf{x}_{k+1} \leftarrow \mathbf{x}_k - \gamma_k \, B_k \nabla f_k, with the step length \gamma_k chosen by a line search
    2. record the step \mathbf{s}_k = \mathbf{x}_{k+1} - \mathbf{x}_k and the gradient difference \mathbf{y}_k = \nabla f_{k+1} - \nabla f_k
    3. update B_k to B_{k+1} by the rank-two formula above: the smallest symmetric modification of B_k satisfying the secant condition B_{k+1} \mathbf{y}_k = \mathbf{s}_k (B_{k+1} stays positive definite because the line search ensures \mathbf{y}_k^\top \mathbf{s}_k > 0)
  3. return the final iterate \mathbf{x}_k

Here \nabla f_k is short for \nabla f(\mathbf{x}_k), and B_k \approx H^{-1} throughout: this B is the traditional quasi-Newton symbol for the inverse-Hessian approximation, nothing to do with the mini-batches B_t of Algorithm 5.2.

Two closing remarks on optim() and minimize(). For problems with many parameters there is method = "L-BFGS-B" (same name in both), a low-memory variant that stores only the last few (\mathbf{s}_k, \mathbf{y}_k) pairs instead of the full d \times d matrix (and accepts box constraints on the parameters). And practically: optim() with BFGS is what you reach for when fitting a model by maximum likelihood in R (minimize() in Python): countless packages in both languages are, under the hood, exactly optim(par, nll, gr, method = "BFGS") or its minimize() twin wearing a nice interface.

5.3 Where you will see all this again

This chapter is a gateway. The same handful of ideas reappears, barely disguised, all over statistics and machine learning:

  • Maximum likelihood, everywhere. Almost every model you will fit from now on is fitted by numerically minimising a negative log-likelihood. Sometimes the optimiser is visible (optim() or minimize() in a package’s source code), sometimes hidden (R’s glm() uses iteratively reweighted least squares, a Newton variant), but it is always there, and now you know what its knobs mean and what its failure modes look like. When a model “fails to converge”, you have seen the picture: a too-large step diverging, or an ill-conditioned likelihood crawling.
  • Neural networks. Training a network is minimising an average loss over millions of observations and millions of parameters: mini-batch SGD is the core engine (usually with the momentum trick of the additional_scrapped_materials notebook), and the popular Adam optimiser adds an adaptive diagonal preconditioner estimated on the fly. You have now implemented the essential parts of it in a few dozen lines of code.
  • Sampling algorithms. When you meet Markov chain Monte Carlo in weeks 8–10 of this module, you will find the same geometry problem in a new costume: a sampler exploring an elongated, ill-conditioned posterior zig-zags just like gradient descent did, and the fix is again preconditioning (there it goes by names like “mass matrix” or “proposal covariance”). The valley picture from this chapter is worth keeping.

The tools were weeks 1–4: vectors and matrices to hold the data, loops to iterate, functions to make the algorithms reusable, and plots to see what is really going on. The ideas were this week’s. Together they are most of computational statistics.
